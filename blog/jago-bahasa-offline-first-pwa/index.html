I built a 23-language learning app with zero dependencies and no build step. Here's what offline-first really takes

By Harasta Rahman Tri Putra (xTheoPutra) · 19 October 2026

I built a 23-language learning app with zero dependencies and no build step. Here's what offline-first really takes

Jago Bahasa ("good at languages" in Indonesian) is a free PWA for learning 23 languages, from Korean and Arabic to Swahili and Ukrainian. It is plain HTML, CSS and ES modules. There is no framework, no bundler, no node_modules, and package.json has no dependencies key at all. You can open the live demo, load it once, switch to airplane mode, and keep studying.

What it contains today, recounted from the repo rather than copied from the README:

  • 23 courses with 442 lessons and 3,563 vocabulary items
  • 23 "book" dictionaries with 168 headwords each (3,864 entries), 2,209 of them with a full definition and example sentence
  • 161 tests, run with nothing but node --test

I didn't write all of that by hand. I built it over about four months with Claude Code as a pair programmer, and the full design log is in docs/SESSION-LOG.md. The interesting part, for me, was not the features but what it took to keep an offline-first app honest.

The service worker is the whole product

If your app has to work offline, the precache list is your release. sw.js holds a VERSION string (currently jb-v3.5.2) and an ASSETS array of 84 entries: the shell, every ES module, all 23 course chunks and all 23 dictionary volumes. Install caches all of it. Activate deletes every cache whose name doesn't match the current version. Then the fetch handler applies three rules:

  • /api/* always goes to the network and is never cached. That's the optional sync backend.
  • Navigations are network-first and fall back to the cached index.html. If even that is missing (first visit made offline), the user gets a small readable offline page, not the browser's error screen.
  • Static assets are cache-first. They never fall back to the HTML shell, because a module request answered with HTML is a hard parse error that takes the whole app down.

On the page side, js/pwa.js shows an "update available" toast. It reloads on controllerchange only if the page already had a controller, so first-time visitors don't get a pointless reload flash.

The honest limitation: cache-first means returning users keep old code until I bump VERSION. That bump is manual. Nothing in the test suite forces it.

Splitting the catalogue into per-language chunks that load on demand made startup much lighter. All chunks are still precached, so lazy loading never breaks offline use. The catch is that every new file has to appear in ASSETS. So tests/assets.test.mjs parses sw.js and fails if any front-end module is missing from the list, or if the list points at a file that doesn't exist.

The bug that 156 green tests couldn't see

For 42 days, the live site served every dictionary but zero lessons.

The root .gitignore had a line data/, meant for the backend's runtime JSON store. Without a leading slash, git matches a data directory at any depth, including js/data/, where all 23 course files live. The files existed on my disk, so the tests passed and git status was clean. They just never reached GitHub, and GitHub Pages returned 404 for every lesson.

The first CI run caught it, because a CI runner clones from git rather than reading my disk. The fix was one character (/data/), plus a test in tests/assets.test.mjs that compares the precache list against what git actually tracks (excerpt):

test("every precached asset is tracked by git, not merely present on disk", (t) => {
  let tracked;
  try {
    tracked = new Set(
      execFileSync("git", ["ls-files", "-z"], { cwd: ROOT, encoding: "utf8" })
        .split("\0")
        .filter(Boolean)
        .map((p) => `./${p}`)
    );
  } catch {
    return t.skip("not a git checkout — nothing to compare the precache list against");
  }
  // …
  const unshipped = [...precached].filter((p) => p !== "./" && !tracked.has(p));
  assert.deepEqual(
    unshipped,
    [],
    `precached but never committed — the deployed site will 404 on these: ${unshipped.join(", ")}`
  );
});

Lesson learned: being on disk doesn't mean you shipped it. Only git decides what ships.

A dictionary should be browsed by its own alphabet

A Korean dictionary isn't sorted A–Z, and neither is a Thai one. js/lexicon.js assigns each headword to a letter tab using the rules a printed dictionary in that script would use:

// js/lexicon.js (excerpt)
export function letterOf(lang, w, r) {
  const src = BY_READING.has(lang) ? r || w : w;
  const chars = Array.from(String(src).trim());
  let ch = chars[0] || "";
  if (lang === "th" && THAI_LEAD_VOWELS.includes(ch)) ch = chars[1] || ch;
  if (ARABIC_BASE[ch]) ch = ARABIC_BASE[ch];
  if (!ch) return "#";
  const code = ch.codePointAt(0);
  if (SCRIPT_OF[lang] === "han" && code >= 0xac00 && code <= 0xd7a3) {
    return HANGUL_LEAD[Math.floor((code - 0xac00) / 588)] || "#";
  }
  // … then alphabet lookup and diacritic folding for Latin, Cyrillic, Greek

Hangul syllables are filed by their leading jamo: each initial consonant covers a block of 588 code points, so plain division finds it. Thai skips the four vowel signs written before their consonant. Arabic files hamza and final forms under the base letter (أ إ آ → ا, ة → ه). Japanese and Chinese are indexed by romaji and pinyin. Latin letters that NFD normalization can't decompose (Ł, Ø, ß) get an explicit map. A test checks that every headword lands in its own letter and that the letter blocks never interleave.

Refusing to fake a voice

Pronunciation uses the browser's built-in text-to-speech. On the stock Windows Chrome I tested, 10 of the 23 languages had no installed voice. The old behaviour handed Arabic text to whatever voice existed, so learners heard English phonetics or silence, and couldn't tell either from a bug. Now the app checks first:

// js/core/ui.js (excerpt)
const base = (lang) => String(lang || "en").toLowerCase().split("-")[0];

export function hasVoice(lang) {
  if (!("speechSynthesis" in window)) return false;
  const list = voices();
  if (!list.length) return true;
  const b = base(lang);
  return list.some((v) => v.lang && base(v.lang) === b);
}

Buttons that can't speak are marked and explained, and the audio-only modes refuse to start. The split("-") is there because of a bug the tests caught: the first version used slice(0, 2), and Tagalog's tag is fil-PH. The first two letters of that are fi, which is Finnish. One test in tests/tts.test.mjs is literally named "Tagalog is fil, and the first two letters of that are Finnish".

Smaller things that still took real work

  • Spaced repetition is an SM-2-lite in js/core/state.js. It has four grades (again/hard/good/easy), starts ease at 2.5 with a floor of 1.3, and puts dictionary words you've starred into the same rotation as lesson words.
  • Exam certificates print the same in light and dark themes. The first real PDF export printed the "Install app" button on every page. In dark mode, with "background graphics" ticked, half the text was invisible. Print colours are now pinned to ink-on-white in @media print. An interaction test emulates print media in both themes, asserts the computed colours match, and checks that the PDF is exactly one page.
  • CSP is script-src 'self' plus one SHA-256 hash for the single inline framebuster script. A test fails if a second inline script ever appears.
  • Randomness for shuffles and exam picks uses crypto.getRandomValues with rejection sampling, never Math.random().

Testing without a framework

npm test is just node --test --test-concurrency=1. The 161 tests cover content shape, i18n key parity, SRS scheduling, exam fairness, the optional backend on a random port, and two browser suites. Those browser suites drive real Chrome over the DevTools Protocol using Node's built-in WebSocket, so they need no Puppeteer or Playwright. They skip themselves if Chrome is missing. On my machine the full run takes about 99 seconds. CI runs it on Node 20 and 22.

One more lesson from CI: the final-exam test used to try only 10 random rounds and passed for weeks while the generator was lopsided (one stage got 9 questions, another 6). At 200 rounds it fails immediately on the old code. A test that samples randomly a few times isn't a guard. It's a lottery.

What it isn't (yet)

  • The UI is available in Indonesian, English and Spanish, and word meanings exist only in those three. The design log and commit messages are mostly in Indonesian.
  • Content depth is uneven. English and Korean have 32 lessons each; the other 21 languages have 18. The dictionaries, by contrast, are identical in size.
  • Pronunciation quality depends on the voices your device has.
  • Accounts in static-hosting mode live in IndexedDB (PBKDF2, 600,000 iterations). That keeps profiles separate on a shared device, but it doesn't protect anything from someone with physical access to the device.
  • No usage numbers to share. It's a side project, and I haven't added analytics.

If you're thinking about building an offline-first app without a toolchain, my takeaway is that the build step you skip comes back as discipline. Your precache list, your .gitignore, and your version bump become the release process, so test them like code.
